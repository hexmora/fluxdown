# 架构介绍

Fluxdown 要处理的，不只是一份写好的 Markdown。它面对的文本还在增长，最后一个标记可能没闭合，屏幕上显示的进度也可能落后于已收到的内容。

这些变化都交给 Core 处理。界面层接收处理后的结果，再把它画出来。先以浏览器中的 React DOM 版为例，跟着一段新文字走一遍：点击步骤可以慢慢看，也可以播放整个过程。

上面按先后顺序展示各层的职责。实际运行时，这些层通过响应式状态连接：输入变化后，依赖它的计算随之更新。

## 用状态闭包组织处理过程

Core 基于 [Stative](../stative/index.md) 构建。Stative 用**状态闭包（state closure）**封装一段状态流：它知道自己依赖什么、如何得到结果，以及需要管理哪些子计算和资源。

可以把它理解成数据处理中的组件。分块是一块，编译是一块，平滑化也可以是一块。每一块有自己的输入和结果，再组合成完整的 Markdown 处理流程。

下面是 Core 的主要组合关系，省略了插件与配置分支。缩进表示组合关系；数据通常从里面的输入层流向外面的输出层。

```text
Core
└─ Renderer                 输出到目标界面
   └─ MapperComposer        组合平滑化与特效
      └─ BlockCompiler      管理各块的编译
         ├─ TextChunker     把文本分成段落等内容块
         └─ CompiledBlockContent × 多个块
            └─ BlockItem    保存内容、位置与可见范围
```

闭包不仅组织代码，也划分生命周期。一个段落被移除，对应的子计算就可以结束；整个 Core 被销毁，它管理的订阅和资源也一起释放。无需在界面组件里逐个寻找和清理它们。

## 从文本到可阅读的内容

### 分块：把变化留在合适的范围里

`TextChunker` 接收当前完整的文本，按 Markdown 结构划分内容块。这里的“块”与网络返回的片段不同：一个网络片段可能跨过好几个段落，一个代码块也可能经过很多次接收才写完。

当末尾继续增长时，内容没变的段落会尽量复用原来的结果，后面的编译层便有机会跳过重复工作。新内容也可能改变块的边界，例如把前一行变成标题，Core 会按新的结构确定受影响的范围。

`patches` 中的原文位置也在这一层分配到对应的块，为后续插入内容做好准备。

### 编译：理解 Markdown，照顾未完成的结尾

`BlockCompiler` 为各块建立独立的编译状态。每个块经过 Markdown 解析、remark 插件和 rehype 插件，得到适合渲染的内容树，也就是 HAST。可以把这棵树想成一份结构化的排版说明：这里是段落，那里是链接，里面还有一段加粗文字。

语法修复也参与这个过程。开启流式修复后，Core 会针对末尾块照顾尚未闭合的语法；前面已经确定的块按正常规则处理。修复服务于当前展示，不会改写应用传入的 `text`。

每个 `BlockItem` 除了保存内容，还提供位置、长度和可见范围。后续处理可以沿用同一份内容，只调整这一刻需要展示多少。

### 映射：让内容按自己的节奏出现

`MapperComposer` 把启用的 mapper 按顺序组合起来。平滑化、末尾渐变、逐字入场等能力都在这一层接入。

平滑化跟踪“已经收到多少”和“已经展示多少”，逐步推进可见范围。特效则为对应内容补充渲染所需的信息。它们建立在编译后的块上，因此一个字正在淡入时，不需要为了这次动画重新解析整篇 Markdown。

平滑化开启时，即使网络暂时没送来新文字，已经收到的内容也能继续逐步显示。

## React 怎样接到 Core

Core 把最后一步留给 `Renderer`。它接收处理后的块与渲染插件，决定最终输出什么，因此可以适配不同的界面框架。

浏览器版 `fluxdown` 和 React Native 版共用 `@fluxdown/react-base`。这一层负责连接 Core 与 React，平台组件再补上容器、主题和具体的显示方式。

其中的 `FluxdownBase` 主要接起下面几件事：

1. **把 props 接成状态。** 将 `text`、配置和插件等输入接到 Stative 状态。组件收到新 props 时，更新已有输入，继续使用同一个 Core。
2. **为每个块建立 React 组件。** `ReactRenderer` 为各块生成 `BlockReconciler`，并使用块的身份作为 key。
3. **订阅对应的变化。** 根组件关注块列表，块组件关注自己的内容。`@fluxdown/react-hooks` 通过 React 的 `useSyncExternalStore` 接起这些订阅，再由渲染插件与插槽生成界面。
4. **随组件结束状态流。** 卸载时销毁 Core，释放它管理的计算与资源。

比如一条消息还在生成最后一段，前面的代码块就不必因为每次新文本到达而重新走完整个解析和渲染流程。输入、编译结果和块的身份没有变化时，可以沿用已有结果；配置或插件发生变化时，相关计算仍会正常更新。

`@fluxdown/react-base-plugins` 提供段落、链接、代码块等共享的渲染逻辑和插槽约定。浏览器插件把段落画成 `<p>`，React Native 插件用 `Text`、`View` 等原生组件来呈现。React Base 本身不添加页面容器或样式，所以这两种界面可以共用块渲染与订阅逻辑。

应用还可以替换平台上的插槽，让代码块带上复制按钮或工具栏，或把一处插入内容变成可交互的卡片。

## Stative 的构建运行时做了什么

Core 用 JSX 描述**状态流的组合**。`TextChunker`、`BlockCompiler` 等标签经由 Stative 自己的 JSX runtime 变成描述，随后由 `render(...)` 创建可读取、可订阅的根闭包。内部的构建过程负责把这些描述连接成实际运行的状态图。

这层运行时主要负责三件事：

- **连接输入。** 普通值、响应式状态和子闭包可以接到同一段计算上，计算结果继续作为下一层的输入。
- **保留正在工作的状态流。** `once` 声明的组合在首次访问时建立，后续由内部的响应式计算接收变化。末尾追加文字时，不必重新搭建整棵状态树。
- **管理归属与清理。** 它记录哪些子闭包和资源属于当前流程，在替换或销毁时清理。外部传入、可能被其他地方共享的状态，仍由创建者管理。

因此，从一棵描述树到持续工作的数据流，中间的连接和生命周期由 Stative 承担，Core 的各层可以专心处理 Markdown。

这里的“构建”指连接状态图；Fluxdown 的 `build` 则配置 Markdown 的解析与编译。

## 一套核心，三种界面

React DOM、React Native 和 ReactLynx 都已经接到同一个 Core，适配关系如下：

```text
@fluxdown/core
├─ @fluxdown/react-base       共享 React 渲染与订阅
│  ├─ fluxdown               浏览器 DOM、CSS 与交互
│  └─ @fluxdown/react-native  原生 Text、View 与样式
└─ @fluxdown/lynx             ReactLynx 的 text、view 与样式
```

ReactLynx 通过自己的 `LynxRenderer` 连接 Core。它的状态订阅和组件生命周期由 `@fluxdown/lynx-plugins` 中基于 `@lynx-js/react` 的 hooks 处理。这条适配路径独立于 React Base，Markdown 解析在 Lynx 的后台线程中运行。

各端的字体、布局、特效和交互由各自的插件实现。它们复用 Core 的分块、语法修复和显示进度，也保留适合当前平台的呈现方式。

接入项目时，直接选择对应的快速开始：[React DOM](./react/quick-start.md)、[React Native](./react-native/quick-start.md) 或 [Lynx](./lynx/quick-start.md)。想自己决定输出形式，可以继续看 [Core 快速开始](./core/quick-start.md)；想了解状态流本身如何组合，可以看 [Stative 的组合计算](../stative/composition.md)。
